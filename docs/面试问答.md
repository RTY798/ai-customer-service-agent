# AI 智能客服 Agent 系统 — 面试问答

## 一、项目整体介绍

### Q1: 请简单介绍一下你这个项目

> 面试官你好，这个项目是一个基于 **LangGraph** 构建的多 Agent 智能客服系统。它模拟了真实客服场景：用户提问 → 系统自动判断意图 → 调用知识库或工具 → 生成回复。整个系统由 5 个专用 Agent 协作完成，涵盖意图路由、RAG 知识库检索、Function Calling 工具调用和工单升级等完整闭环。

> 技术栈方面，后端用 **FastAPI** 提供 REST API 和 SSE 流式推送，Agent 编排层使用 **LangGraph** 的 StateGraph，前端是 **Next.js 16 + Tailwind CSS v4**。我选择了 **DeepSeek** 作为 LLM 后端，因为它性价比高，在 API 调用方式和 OpenAI 完全兼容。

### Q2: 为什么要做这个项目？解决了什么实际问题？

> 传统客服系统要么是人工回复，要么是简单的关键词匹配机器人，处理不了复杂的语义和上下文关联。我想做一个能像真人客服一样「思考」的系统——不是简单匹配关键词，而是真正理解用户意图，分配合适的 Agent 去处理，最终给出有依据的回复。这个项目非常贴近现在企业对 AI Agent 落地的需求，也让我完整实践了多 Agent 架构的工程化过程。

## 二、Agent 架构设计（核心考点）

### Q3: 为什么选择 LangGraph 而不是 CrewAI 或其他框架？

> **LangGraph** 比 CrewAI 更底层、更灵活。CrewAI 是高层封装，适合简单的角色协作，但当你需要精细控制 Agent 之间的流转逻辑、条件分支、状态共享时，LangGraph 的 StateGraph 模型更合适。具体来说：

> 1. **StateGraph 模型**：将整个工作流定义为一个状态机，每个 Agent 节点读写共享状态，非常适合"路由→处理→汇总"这种流程
> 2. **条件边**：Router Agent 输出意图分类后，通过 `add_conditional_edges` 动态路由到不同 Agent，这是 CrewAI 很难做到的
> 3. **调试友好**：每个节点的输入输出都是显式的，中间状态可以随时检查
> 4. **简历价值**：LangGraph 是业界主流方案，面试官更认可

### Q4: 5 个 Agent 是怎么分工协作的？画一下流程图

> 整个流程是这样的：

```
用户输入 → Router Agent（意图分类）
               │
     ┌─────────┼──────────┐
     ▼         ▼          ▼
Knowledge   Tool    Escalation
  (RAG)    (函数调用)  (工单升级)
     │         │          │
     └─────────┼──────────┘
               ▼
         Summary Agent
          (整合回复)
```

> - **Router**：不做具体处理，只负责分类，输出 `order_query / product_inquiry / complaint / general` 四种意图
> - **Knowledge**：收到"产品咨询"类问题，去做知识库检索，找到相关文档后用 LLM 合成回答
> - **Tool**：收到"订单查询"类问题，调用对应的工具函数（订单查询、物流追踪等）
> - **Escalation**：收到"投诉"类问题，生成结构化工单转人工
> - **Summary**：无论走哪条路，最后都汇总到这里，整合所有信息生成自然语言回复

### Q5: Agent 之间是怎么通信的？状态怎么传递？

> LangGraph 的核心是 **AgentState**，它是一个 TypedDict，包含了 `user_message`、`thought_chain`、`retrieved_docs`、`tool_results` 等字段。每个 Agent 节点都接收这个状态、处理、然后返回更新后的状态子集。

> 关键设计点：**状态是累加而非替换的**。比如 thought_chain 字段，每个 Agent 不是覆盖它，而是通过 `existing + [new_thought]` 的方式追加，这样最终得到完整的 Agent 思考链，便于前端展示。

> 举个例子：
> 1. Router 处理 → 在 thought_chain 追加 `{agent: "router", status: "completed", ...}`
> 2. Knowledge 处理 → 再追加 `{agent: "knowledge", ...}`
> 3. Summary 拿到完整的 thought_chain → 生成回复 → 前端展示给用户

## 三、RAG 知识库（高频考点）

### Q6: 你的 RAG 是怎么实现的？用了什么向量数据库？

> 最初我设计的是用 ChromaDB，但实际部署时遇到了两个问题：一是 Windows 上 ChromaDB 依赖的 sqlite3 版本不够，二是 ChromaDB 的依赖太重（onnxruntime 就 60MB）。所以我换成了**轻量级的关键词匹配方案**。

> 具体实现：
> 1. **文档分块**：把 9 篇中文产品文档（FAQ、退换货政策、配送说明等）按段落分块
> 2. **分词**：中文按单字切分，英文按空格切分，去重后得到 token 集合
> 3. **相似度计算**：用 **Jaccard 相似度**（两个集合交集大小 ÷ 并集大小）对查询和文档进行打分
> 4. **检索**：取 top-3 最相似的文档块，送入 LLM 合成最终回答

> 这个方案虽然比不上向量检索的语义理解能力，但胜在零依赖、零外部服务，而且对高频常见问题的匹配效果已经够用。

### Q7: 如果让你改进 RAG 部分，你会怎么做？

> 我会从几个方向优化：
> 1. **换向量检索**：用 sentence-transformers 做中文文本向量化，然后用余弦相似度检索，语义匹配效果会好很多
> 2. **HyDE 策略**：先让 LLM 根据问题生成一个假设性答案，再用这个答案去检索，能提升召回率
> 3. **重排序**：初检索取 top-10，用一个 lightweight 的 reranker 模型重新排序，取 top-3
> 4. **文档更新**：增加动态文档加载机制，支持运行时添加新文档，而不是硬编码 9 篇

## 四、Function Calling（加分考点）

### Q8: 你的 Tool Agent 是怎么实现的？Function Calling 是什么原理？

> Tool Agent 的核心是 OpenAI 兼容的 **tools API**。我在请求 LLM 时，传入一个工具列表（JSON Schema 格式），每个工具定义了名称、描述、参数结构。LLM 根据用户的提问，自动判断该调用哪个工具、填入什么参数。

> 比如用户问"查询订单 ORD-001"，LLM 会返回一个 tool call：
> ```json
> {
>   "function": "query_order",
>   "arguments": {"order_id": "ORD-001"}
> }
> ```

> 我这边收到后，实际执行对应的 Python 函数拿到结果，再送回给 LLM 让它生成自然语言回复。**整个过程相当于 LLM 在做"意图识别 + 参数提取"，具体的业务逻辑由代码执行**。

### Q9: 你实现了哪几个工具函数？数据是真实的吗？

> 我实现了 4 个工具函数：
> 1. `query_order(order_id)` — 查询订单状态和详情
> 2. `track_shipment(order_id)` — 查询物流信息
> 3. `check_return_policy(category)` — 查询某类商品的退换货政策
> 4. `get_product_info(product_id)` — 查询产品详情

> 数据是**模拟数据**，我预先构建了几个示例订单（ORD-001/002/003）和产品（P001/P002/P003），没有接入真实的电商系统。但在架构上，这些函数完全可以对接真实数据库或第三方 API，因为接口设计是标准的输入输出格式。

## 五、工程化与架构（加分考点）

### Q10: 你们用了 SSE 流式推送，为什么不用 WebSocket？

> **SSE（Server-Sent Events）** 适合这个场景的原因：
> 1. **单向通信**就够了：客服场景只需要服务端推送 Agent 思考过程给前端，不需要前端实时给后端发消息
> 2. **实现简单**：FastAPI 原生支持 StreamingResponse，几行代码就能实现
> 3. **HTTP 协议**：不走额外的协议握手，防火墙兼容性更好

> WebSocket 适合双向实时通信的场景（比如在线协作编辑、游戏），在这个项目里有点 overkill。

### Q11: 前端是怎么展示 Agent 思维链的？

> 前端在收到 SSE 事件流后，将每个 Agent 节点的状态（running/completed）和详细信息展示出来。我设计了一个 **AgentThoughtChain** 组件：

> - 默认折叠状态显示一排彩色圆点（绿色=完成，黄色=运行中，红色=报错）
> - 展开后按时间顺序展示每个 Agent 的处理过程
> - 每个节点显示 Agent 名称标签（中文：分流/知识库/工具等）、处理状态、输入输出摘要

> 这个设计让用户能看到 AI 的"推理过程"，而不是直接得到一个黑盒回答，**透明感和信任感会强很多**。也是面试时候可以重点展示的亮点。

### Q12: 项目是怎么部署的？

> 我写了 **Docker Compose** 编排文件，包含两个服务：
> 1. **backend**：Python 3.13 slim 镜像，FastAPI + LangGraph
> 2. **frontend**：Next.js 多阶段构建，production 模式运行

> 通过 `docker-compose up --build` 一键启动，后端有健康检查，前端等后端就绪后才启动。环境变量（API Key）通过 `.env` 文件注入，不会硬编码在代码里。

### Q13: 错误处理是怎么做的？

> 我在每一层都做了错误兜底：
> 1. **LLM 调用失败**：如果 DeepSeek API 超时或返回异常，后端会返回友好的中文错误提示，而不是直接崩溃
> 2. **Function Calling 异常**：如果工具函数执行出错（比如查不到订单），LLM 会告诉用户"查不到该订单信息"
> 3. **前端容错**：如果 API 调用失败，前端会显示错误消息，而不是白屏
> 4. **降级策略**：所有 Agent 都有兜底回复逻辑，确保不会因为某个 Agent 异常导致整个对话崩溃

## 六、面试追问（压力测试）

### Q14: 如果用户量很大，这个系统怎么应对高并发？

> 目前的单进程架构确实扛不住高并发。如果要上线，我会做这几件事：
> 1. **异步处理**：LangGraph 调用是同步的，可以用消息队列（如 RabbitMQ）把请求异步化
> 2. **水平扩展**：后端无状态，可以多开几个 uvicorn worker 或 Kubernetes 多副本
> 3. **缓存**：常见问题的 LLM 回复可以缓存起来（比如 Redis），命中缓存就不需要调用 LLM
> 4. **限流**：加一个 rate limiter，防止被刷接口

### Q15: 你觉得这个项目最大的难点是什么？

> 对我来说最大的难点是 **Python 版本兼容问题的处理**。项目初期设计用的是 ChromaDB，但我的本机 Python 3.8 不支持，升级到 3.13 后 ChromaDB 的依赖又装不上。最后我决定放弃 ChromaDB，自己用纯 Python 实现了一个轻量级的关键词检索方案。「做减法」也是一种工程能力。

> 另外 **LangGraph 的调试**也不太直观。AgentState 是 TypedDict，但 Graph 运行过程中状态是隐式传递的，我花了些时间理解每个节点如何读写状态、如何避免覆盖已有的 thought_chain。

### Q16: 这个项目距离真正的生产环境还有多远？

> 核心架构已经跑通了，但距离生产还有几件事：
> 1. **知识库**：需要连接真实的产品数据库和文档系统
> 2. **工具函数**：需要对接真实的后台 API
> 3. **安全加固**：加认证鉴权、API 限流、输入过滤
> 4. **监控**：加日志收集、调用链追踪、LLM 调用成本监控
> 5. **测试**：目前缺少自动化测试，需要补充单元测试和集成测试

> 但作为面试项目，**核心价值已经体现了**：多 Agent 架构设计、LangGraph 编排、RAG、Function Calling、SSE 流式推送、Docker 容器化——这些都是面试官想看的东西。
